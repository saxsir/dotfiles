# post-pr-review-comments

会話中のレビュー指摘事項を、GitHub PRのインラインコメントとして投稿するスキル。
レビュー分析自体は行わず、**既にある指摘をPR上の正しい行に正しいフォーマットで投稿する**ことに集中する。

## 前提条件

- `gh` CLI がインストール済みで認証済みであること
- 対象PRのリポジトリに対して書き込み権限があること
- 会話中にレビュー指摘事項が存在すること（なければ先にレビューを実施する）

## 投稿前のチェックリスト

投稿する前に以下を確認する。1つでもNoなら修正してから投稿する：

- [ ] 会話中の**全ての指摘**がコメントに含まれているか？（漏れがないこと）
- [ ] 各コメントの行番号を検証コマンドで確認したか？
- [ ] suggestion ブロックの内容は対象行の完全な置換か？（部分的な断片ではないこと）
- [ ] コメントは断定的に書かれているか？（「確認してください」ではなく「〜が間違っています」）

## ワークフロー

### Step 1: PR情報の取得

```bash
# PR番号からリポジトリを特定（カレントリポジトリのPRの場合）
gh pr view <PR番号> --json number,title,state,headRefName

# 別リポジトリの場合
gh pr view <PR番号> --repo <owner/repo> --json number,title,state,headRefName
```

PRがOPEN状態であることを確認する。MERGED/CLOSEDの場合はユーザーに伝えて確認を取る。

### Step 2: diffの取得と行番号マッピング

```bash
gh pr diff <PR番号> [--repo <owner/repo>] > $TMPDIR/pr<PR番号>.diff
```

指摘対象の行番号を特定する。これが最も重要かつ間違えやすいステップ。行番号が1つでも間違うと API が 422 エラーを返すか、意図しない行にコメントが付く。

#### 行番号の算出方法

GitHub Review APIの `line` パラメータは **変更後ファイルの行番号** を使う。

**新規ファイル（ADDED）の場合:**

1. diff内でファイルのヘッダー部分の行数を数える（`diff --git`〜`@@ -0,0 +1,N @@` まで。通常6行）
2. `grep -n` でdiff内の対象テキストの行番号を見つける
3. `ファイル内行番号 = diff内行番号 - ヘッダー行数`

```bash
# 手順: まずgrepで指摘対象を含む行のdiff内行番号を特定
grep -n "対象テキスト" $TMPDIR/pr<PR番号>.diff

# ヘッダー行数を確認（通常6行だが、ファイルごとに異なる可能性あり）
grep -n "^@@" $TMPDIR/pr<PR番号>.diff | head -5
```

**既存ファイル（MODIFIED）の場合:**
- `@@ -a,b +c,d @@` ヘッダーの `+c` が変更後ファイルの開始行番号
- そこから `+` 行と空白行（コンテキスト行）をカウントして目的の行番号を算出
- **`-` で始まる行（削除行）はカウントしない**
- 複数の `@@` ハンクがある場合は、対象行を含むハンクから起算する

#### 行番号の検証（必須・全コメントに対して実行する）

**算出した行番号は必ず検証する。**「たぶん合っている」は許容しない。

**新規ファイル（ADDED）の場合:**
```bash
# diffからファイル内容を抽出し、特定行を表示（全行が + で始まる前提）
awk 'NR>=<ヘッダー行数+1>{sub(/^\+/,""); print}' $TMPDIR/pr<PR番号>.diff | sed -n '<行番号>p'
```

**既存ファイル（MODIFIED）の場合:**
```bash
# + 行と空白行（コンテキスト行）のみカウントし、- 行はスキップ
awk '/^@@/{match($0,/\+([0-9]+)/,a); cur=a[1]-1; next} /^[+ ]/{cur++; if(cur==<行番号>){sub(/^[+ ]/,""); print; exit}} /^-/{next}' $TMPDIR/pr<PR番号>.diff
```

表示された内容が指摘対象の行と**完全に一致する**ことを確認する。一致しなければ行番号を再計算する。

**全てのコメントの行番号を一括で検証するのが効率的（新規ファイルの場合）:**
```bash
for line in 123 191 240 241 243 377; do
  echo "L${line}: $(awk 'NR>=7{sub(/^\+/,""); print}' $TMPDIR/pr<PR番号>.diff | sed -n "${line}p")"
done
```

### Step 3: コメントの構成

各指摘を以下の形式で整理する：

| フィールド | 内容 |
|---|---|
| `path` | 変更対象ファイルのパス（diffの `b/` 以降） |
| `line` | 変更後ファイルの行番号（Step 2で算出） |
| `body` | コメント本文（Markdown形式） |

#### コメント本文のフォーマット

指摘には種別を示す絵文字プレフィックスを付ける：

- `🔧` — 要修正（事実誤り、バグ）
- `💡` — 提案（改善案、より良い方法）
- `❓` — 質問（意図の確認、設計判断の理由）
- `📝` — 軽微（typo、フォーマット）

#### コメントのトーン

レビューコメントは**断定的かつ根拠付き**で書く。レビュイーが何をすべきか迷わないようにする。

**良い例:**
> 🔧 `demand_id` が間違っています。
> - ここ: `20`
> - 実際（`batch_config.yaml`）: **`71`**

**悪い例（曖昧すぎる）:**
> 🔧 `demand_id` について確認です。値が正しいことを確認してください。

根拠となるファイルパスや確認コマンドを添えると、レビュイーが自分で検証できて信頼性が上がる。

#### suggestion ブロック

修正案が明確な場合は、GitHub の suggestion 機能を積極的に使う。レビュイーがワンクリックで修正を適用できるため、修正の摩擦が下がる。

````markdown
🔧 `demand_id` が間違っています。実際は `71` です。

```suggestion
| bidder_yahoo | 71 | Yahoo レポート確定時刻 | 23:30 |
```
````

**suggestion ブロックのルール:**
- 対象行の **完全な置換後テキスト** を書く（差分ではなく行全体）
- 複数行にまたがる場合は `line` の代わりに `start_line` と `line`（終了行）を使う
- suggestion を含むコメントは対象行が `+`（追加行）でなければならない

### Step 4: レビューの投稿

全コメントを1つのレビューとしてまとめてAPIで投稿する。コメントを1つずつ投稿してはいけない（通知が大量に飛ぶため）。

```bash
cat > $TMPDIR/pr_review.json << 'ENDJSON'
{
  "event": "COMMENT",
  "body": "レビュー全体のサマリー",
  "comments": [
    {
      "path": "path/to/file.md",
      "line": 42,
      "body": "🔧 指摘内容\n\n```suggestion\n修正後の行\n```"
    },
    {
      "path": "path/to/another.py",
      "line": 15,
      "body": "💡 提案内容"
    }
  ]
}
ENDJSON

gh api repos/{owner}/{repo}/pulls/<PR番号>/reviews \
  --method POST \
  --input $TMPDIR/pr_review.json
```

#### event の使い分け

| event | 意味 | 使うとき |
|---|---|---|
| `COMMENT` | コメントのみ | 指摘はあるが承認/却下の判断を含まないとき（デフォルト） |
| `APPROVE` | 承認 | ユーザーが明示的にapproveを指示したとき |
| `REQUEST_CHANGES` | 変更要求 | ユーザーが明示的にrequest changesを指示したとき |

**デフォルトは `COMMENT`**。`APPROVE` や `REQUEST_CHANGES` はユーザーが明示的に指示した場合のみ使う。

### Step 5: 結果の報告

投稿が成功したら、投稿したコメント数とPRのURLを報告する：

```
6件のインラインコメントを投稿しました: https://github.com/<owner>/<repo>/pull/<PR番号>
```

## エラーハンドリング

- **422 Unprocessable Entity**: 行番号が不正な場合に発生する。行番号を再計算してリトライする。
- **403 Forbidden**: 書き込み権限がない。ユーザーに権限を確認するよう伝える。
- **404 Not Found**: PR番号またはリポジトリが間違っている。

## 注意事項

- 投稿前にユーザーへ確認を取る（投稿は取り消せないため）
- 1つのレビューにまとめて投稿する（個別投稿すると通知が大量発生）
- レビュー本文（`body`）にはサマリーを書く。指摘がない場合は空文字でもよい
- CLAUDE.md のPRスタイルルールがあればそれに従う（口調、絵文字の使い方など）
