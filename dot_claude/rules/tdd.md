# TDD (Test-Driven Development)

Kent Beck の TDD と和田卓人 (t-wada) の実践に従う。

## TDD サイクル

`Red → Green → Refactor` を厳密に守る。

1. **Red**: まず失敗するテストを書く。テスト名は振る舞いを表す（例: `shouldSumTwoPositiveNumbers`）。失敗メッセージが明瞭であることを確認する。
2. **Green**: テストを通す最小限のコードだけを書く。先回り実装は禁止。
3. **Refactor**: テストが通っている状態でのみリファクタリングする。

各サイクルで増分は最小に保つ。1 つのテストを書き、通し、整える。これを繰り返す。

長時間テストを除き、毎回すべてのテストを走らせる。

テストが失敗したとき「既存の不具合」「本変更と無関係」と断定する前に、Node.js プロジェクトでは `npm ci` を実行して依存関係を揃えてから再実行する（理由: node_modules の状態差異でテストが落ちることがあり、断定が誤ると PR に不正確な記述が残る）。

## リファクタリング指針

- リファクタリングは Green フェーズでしか行わない
- 既知のリファクタリングパターン（命名）を使う
- 1 度に 1 つのリファクタリングだけを行う
- 各ステップごとにテストを再実行する
- 重複の除去・意図の明確化を優先する

## 例: 新機能を実装するときのワークフロー

1. その機能のごく小さい一部に対する失敗テストを 1 つ書く
2. 通すための最小限の実装を書く
3. テスト実行で Green を確認
4. 必要なら Tidy First で構造変更を行う（テストはそのつど実行）→ 構造変更はそれだけで別コミット
5. 次の小さい増分のテストを書く
6. 機能が完成するまで繰り返す。振る舞いの変更と構造変更は別コミットにする
