# 委譲 (Delegation)

高コストモデル (Fable / Opus) で動いているときはオーケストレーターであって実行役ではない。判断・計画・統合・最終検証だけを自分に残し、それ以外は安価なモデルに降ろす。高コストモデルの context を判断に残し、全体の token コストを抑えるためだ。

## 着手時の難易度判定

着手前にタスクを 3 段に分け、判定と実行者を着手時の一言に 1 行で書く。完了報告に回すと、ユーザーが誤りを直すには手遅れになる。

| 段 | 内容 | 実行者 |
|---|---|---|
| 機械的 | 読み込み、観点抽出、grep、大量取得、定型修正、戻りの大きい MCP 呼び出し (read-only で要約だけ受け取る) | `model: sonnet` の subagent |
| 明確な実装 | 完了条件 (通すテスト名・実行コマンド・確認する出力・閾値) を宣言できる単位 | `model: sonnet` の subagent。繊細な箇所は `opus` |
| 判断 | 計画、設計、レビュー、統合、最終検証、原因不明の調査 | 自分 |

「原因不明」は、仮説が 1 つも立たないか、再現手順が無いときだけを指す。仮説の検証は機械的段に入る。subagent の成果を統合・検証する立場は、その前の読み込みを自分でやる理由にならない。

読み込みは、要約で足りるなら (欲しいのが結論・所在・件数) 読み始める前に降ろす。原文の言い回しが判断材料になるもの (レビュー対象の文面、これから直す箇所) と、1〜2 ファイルや 1 コマンドで済む確認は自分で読む。

実装で「これぐらいなら自分で」と感じたら、委譲プロンプトを書き直して降ろす。完了条件を宣言できる粒度まで分解できないうちは委譲せず、計画を詰める。

## dude の flow での実装

`implement-work` がメインに実装を認める場面 (設計判断の無い lane の manual、inline、理由付きの manual) と、完了ゲートの Verify で未達の criterion を実装する場面も worker に降ろす。計画がある変更は `implement-work` の既定の実行方法へ、それ以外は Agent tool を直接起こす。「分割できない」が理由の manual は、計画を詰め直して割る。割れないが完了条件は宣言できるなら 1 体の worker (`model: opus`) に降ろし、宣言できないなら `plan-work` に戻す。

次の書き込みはメインが行う。何を直すかが worker から返っているか、merge 途中の tree をその workspace で扱う必要があるためだ。

- 完了ゲートや `pr-to-ready` で判定役が accept した修正の適用
- `simplify-code` で採用した提案の適用
- `pr-to-ready` で診断の worker が返した CI 修正の適用
- base を取り込んだときの conflict の解消

## 委譲の書き方

- `model` を省くと `CLAUDE_CODE_SUBAGENT_MODEL` で sonnet になる。built-in の `Explore` / `Plan` はメインのモデルを継承する (Explore は hook が sonnet を補う)。高コストモデルが要るときは `model` を明示する。
- dude の marked worker は tier に対応する agent 定義で起こす。`high` は `subagent_type: dude:high-tier`、`highest` は `dude:highest-tier`。型も `model` も指定しないと sonnet で動く。
- 所在・件数だけ欲しい読み込みは `Explore` に降ろす (CLAUDE.md と rules を読まないので安い)。全文を読んだうえでの要約と、rules に従う作業は general-purpose にする。
- 委譲プロンプトには完了条件・触るファイル・報告形式を入れる。実装なら次も入れる。聞ける相手がいない前提で最後までやる (止まるのは進めようがないときと危険な操作の前だけ)。test / typecheck / build を走らせて出力を報告し、走らせなかった検証を名指しする。依頼外の機能・テスト・docs・refactor は足さず報告末尾の提案に留める。subagent を起こさない。検証の省略と依頼外の追加は返り値から見分けにくい。
- 起動後は、その結果に依存しない作業を先に進める。
- 返り値は検証してから採る。tool 使用回数が件数に対して極端に少ない、内容が既知の事実と食い違う、は孫 subagent による捏造のシグナル。
- 指摘を直しては再レビューするループ (委譲した成果物の検収を含む) は dude の Loop convergence で止める。回す前に 1 ラウンドの範囲を決める。「同じ指摘」は同じ場所を同じ理由で指すものとし、言い回しが変わっていても、直したはずの指摘が再び出てきても同じとみなす。

## 避ける

- 大規模・繊細・原因不明の作業を Sonnet に降ろす (品質劣化の往復が一番高くつく)。
- 自己検証・二重チェック目的の subagent (過検証になる)。例外は dude の完了ゲートと、ユーザーが起動したレビュー。書く側レビューは Sonnet に降ろさない。

検出系の worker (レビュー・security-review) の tier は、修正側と独立に決める。見逃しが後段の gate (人が読む PR や plan、CI、後のレビュー) の読む範囲に残るなら `high`、どこにも現れないなら `highest`。
