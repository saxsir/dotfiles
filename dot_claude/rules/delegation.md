# 委譲 (Delegation)

高コストモデル (Fable / Opus) で動いているときはオーケストレーターであって実行役ではない。目的は全体の token コストを抑えること。判断・計画・統合・最終検証だけを高コストモデルに残し、それ以外は安価なモデルに降ろす。

## 着手時の難易度判定

作業を始める前にタスクを 3 段に分け、判定と実行者を着手時の一言か完了報告に 1 行で書く。判定が見えていればユーザーが誤りを直せる。

| 段 | 内容 | 実行者 |
|---|---|---|
| 機械的 | 資料・ファイルの読み込み、観点抽出、grep、大量取得、定型修正、戻りの大きい MCP 呼び出し (Drive / Slack 等は read-only で要約だけ受け取る) | `model: sonnet` の subagent |
| 明確な実装 | 完了条件 (通すテスト名・実行コマンド・確認する出力・閾値) を宣言できる単位 | `model: sonnet` の subagent。繊細な箇所は `opus` |
| 判断 | 計画、設計、レビュー、統合、最終検証、原因不明の調査 | 自分 (Fable / Opus) |

1 ファイルを読む・1 コマンドで確かめる程度は自分でやってよい。3 ファイルを超えて読み始めたら機械的段に入ったと見て降ろす。「これぐらいなら自分で」と感じたら委譲プロンプトが甘い信号として扱い、指示文を書き直す。

明確な実装は完了条件を宣言できる粒度まで分解できたら降ろす (実行手段は `subagent-driven-development`)。分解できないうちは委譲せず、まず計画を詰める。

## 委譲の書き方

- `Agent` 呼び出しは `model` を常に明示する。省略 (`inherit`) は親モデル継承で、Fable / Opus 実行時に機械的作業まで高コストで走る。built-in の `Explore` / `general-purpose` / `claude-code-guide` も同じ。
- プロンプトは self-contained に書く (subagent は自分の context を持たない)。ゴール、完了条件、触るファイル、報告形式を入れる。構造は `dispatching-parallel-agents` skill に従う。
- 起動したら結果待ちで手を止めず、その結果に依存しない作業を先に進める。Agent tool はバックグラウンドで返り、完了は通知で届く。
- 返り値を鵜呑みにしない。件数の多い委譲で subagent が孫 subagent を生み、対象を読まずに内容を捏造した例がある。tool 使用回数が件数に対して極端に少ない、返ってきた内容が既知の事実と食い違う、が検知シグナル。

## 避ける

- 大規模・繊細・原因不明の作業を Sonnet に降ろす (品質劣化の往復が一番高くつく)。
- 自己検証・二重チェック目的の subagent (モデル自身の検証と重複して過検証になる)。ユーザー起動のレビューゲートは [[review-cycle]] が正で、書く側レビューは最良モデルに当てる (Sonnet に降ろさない例外)。

Why: 高価なモデルの context は判断・レビューに使い、量産できる実行は安価なモデルに降ろすのが費用対効果で正しい。
